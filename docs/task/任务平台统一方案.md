# 任务平台统一方案（Task Platform Unification）

## 1. 背景与现状

当前仓库中“任务”概念分散在多套实现里，导致前后端对齐成本高、状态口径不一致、运行追踪割裂：

- **运行任务（任务中心）**：`/api/v1/async/tasks`（前端 TaskCenter 使用），具备列表、进度、WebSocket 推送、软删除等平台能力。
- **执行编排任务**：`/api/v1/executions`（ExecutionTask/SubTask），偏“引擎内部编排”，负责拆分子任务与调度。
- **任务模式/模板**：`/api/v1/task-mode/...`（TaskMode），具备版本化、QA、审计日志、备份、缓存等“配置管理”能力。
- **流水线作业**：`/api/v1/pathway/...`（Pathway Pipeline/Job/Source），用子进程运行 DAG/linear 作业，运行态主要在进程内存。

统一目标是：**平台只暴露一套稳定的“任务中心（TaskRun）”契约**，其他领域实现通过适配器接入；同时把“模板（TaskTemplate）”从“运行实例（TaskRun）”中剥离，形成可复用闭环。

## 2. 统一后的核心抽象

### 2.1 TaskTemplate（任务模板/模式）

面向管理与复用：

- 可版本化（版本历史）
- 可审计（操作日志，before/after）
- 可加密字段（描述、QA、日志内容等）
- 支持备份导入导出

建议对外语义与路由命名为：`task-templates`，并保留 `task-mode` 兼容窗口。

### 2.2 TaskRun（任务运行实例）

面向平台任务中心与可观测性：

- 标准字段：`task_type / status / progress / msg / step / result / error / user_id / created_at / updated_at / deleted`
- 能力：创建、查询、分页列表、软删除、进度回写、实时推送

推荐以现有 `AsyncTask` 体系为主干演进为 TaskRun，以保持前端 TaskCenter 契约稳定。

### 2.3 ExecutionGraph（执行编排内部结构）

面向复杂执行编排：

- ExecutionTask/SubTask/ExecutionLog（依赖关系、执行顺序、状态机、乐观锁等）
- 不建议直接作为前端任务中心数据源
- 通过引用关系接入 TaskRun（ref/extend）

### 2.4 PathwayJob（流水线作业）

面向长驻或批处理数据管道：

- 数据源注册（Source）
- Pipeline/Job 持久化（Job）
- 子进程运行（multiprocessing）
- metrics/节点状态注入（当前为模拟/简化形态）

建议通过 TaskRun 统一追踪，并将 metrics 作为扩展事件/扩展字段承载。

## 3. 统一底层任务引擎服务（Task Engine Service）

### 3.1 职责边界

Task Engine Service 作为平台底座，统一承载：

- 运行管理：start/stop/cancel/retry（按适配器能力分级）
- 事件总线：progress/status/log/metrics 统一事件模型，统一落库与推送
- 适配扩展：不同领域任务通过 Adapter 接入，不强行重写业务逻辑

### 3.2 统一事件模型（TaskEvent）

建议平台统一事件字段：

- `percent`：0-100
- `status`：平台状态枚举
- `msg`：可读信息
- `step`：可机器识别的阶段名（用于 UI/统计）
- `extend`：扩展字段（例如 execution\_task\_id、pathway\_job\_id、metrics 等）

### 3.3 平台状态枚举与映射

平台建议统一状态：

- `PENDING | RUNNING | SUCCESS | FAILED | CANCELLED`

领域状态映射建议：

- AsyncTask：沿用 `PENDING/RUNNING/SUCCESS/FAILED`
- Execution：`SPLITTING/READY/...` 映射为 `RUNNING`，用 `step` 区分阶段
- Pathway：`created/running/stopped/failed`
  - 用户 stop：映射为 `CANCELLED`
  - 自然结束：映射为 `SUCCESS`（需先确认作业语义：批处理 vs 常驻流式）

### 3.4 Adapter 分层

建议四类 Adapter：

- **AsyncTaskAdapter（平台标准实现）**：复用现有 `async_task/async_task_log/task_progress/ws_manager`。
- **ExecutionTaskAdapter**：创建 ExecutionTask -> 启动拆分/调度 -> 将阶段事件映射为 TaskEvent 并回写 TaskRun。
- **PathwayAdapter**：创建/启动 PathwayJob（进程）-> 将 job 状态与 metrics 映射为 TaskEvent 并回写 TaskRun。
- **CeleryAdapter（横向扩展）**：将任务发送到 Redis broker，由 Celery Worker 在独立进程或集群中执行，并将状态变更通过 DB/Redis 统一推回 TaskRun。

## 4. 对外 API 统一建议

### 4.1 运行任务（TaskRun，面向前端）

推荐统一为：

- `POST /api/v1/tasks`
- `GET /api/v1/tasks`
- `GET /api/v1/tasks/{id}`
- `PATCH /api/v1/tasks/{id}/progress`（内部回写）
- `DELETE /api/v1/tasks/{id}`
- `DELETE /api/v1/tasks/completed`
- `WS /api/v1/tasks/ws?user_id=...`

兼容策略：

- 保留 `/api/v1/async/tasks` 作为 alias（内部转调新实现），前端可零改动或小改动迁移。

### 4.2 模板（TaskTemplate，面向管理）

推荐新增：

- `POST /api/v1/task-templates`
- `GET /api/v1/task-templates`
- `GET /api/v1/task-templates/{id}`
- `PUT /api/v1/task-templates/{id}`
- `POST /api/v1/task-templates/{id}/status`
- `GET /api/v1/task-templates/{id}/versions`
- `GET/POST /api/v1/task-templates/backup/...`

兼容策略：

- 保留 `/api/v1/task-mode/...` 作为 alias。

### 4.3 从模板发起运行（闭环）

推荐：

- `POST /api/v1/task-templates/{id}:run`（或 `POST /api/v1/tasks` 传 `template_id`）
- 创建 TaskRun，并把 `template_id` 写入 ref/extend；由 Dispatcher/Adapter 选择执行器。

## 5. Pathway（流水线）纳入统一引擎的专项要求

### 5.1 重启一致性（Reconcile）

当前 Pathway 引擎运行态在内存（active\_jobs），服务重启后会丢。统一方案要求：

- 启动时扫描 DB 中 status=running 的 job，与当前进程态对齐
- 对齐策略：
  - 引擎未运行但 DB 显示 running：标记为 stopped/failed（或尝试恢复，取决于作业语义）

### 5.2 Metrics 的承载方式

metrics 不建议写入 TaskRun 通用字段，推荐：

- 作为 TaskEvent.extend 定期上报
- 或建立独立 metrics 表/存储（后续演进）

### 5.3 Secrets 加密 key 的治理

Pathway secrets 加密必须固定 key：

- 强制要求配置 `PATHWAY_ENCRYPTION_KEY`
- 未配置时应视为配置错误（避免重启后历史 secrets 无法解密）

## 6. 迁移路线（按风险由低到高）

- Phase 0：固化平台状态与事件模型；盘点 Pathway 作业语义与 stop 语义映射。
- Phase 1：TaskMode 增加 `task-templates` 新路由（保留 `task-mode` 兼容）；修正过期文档与命名。
- Phase 2：新增 `/api/v1/tasks`（TaskRun）并用 async\_tasks 复用实现；保留 `/api/v1/async/tasks` alias。
- Phase 3：引入 Dispatcher/ExecutionTaskAdapter，把 ExecutionTask 接入 TaskRun，并回写进度与关联 ID。
- Phase 4：提供模板一键运行（template -> run），形成闭环。
- Phase 5：逐步收敛旧接口，对外只保留 `/tasks`（运行）与 `/task-templates`（模板）。

多实例/多 worker 下的作业统一调度与恢复”也做到生产级（例如把作业启动迁移到你们已有的 task worker / redis stream 体系里），沿着现有 openclaw/task\_stream 的能力继续
