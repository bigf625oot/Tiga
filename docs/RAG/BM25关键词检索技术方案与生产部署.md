# BM25 关键词检索技术方案与生产部署

## 1. 背景与现状

当前 RAG/QA 主链路的检索主要依赖向量库与图谱检索；代码注释提到“BM25 关键词检索”，但在实际调用链路中未接入 BM25 索引与 BM25 打分逻辑（仅存在少量字符串包含/覆盖度扫描作为弱降级）。因此在以下场景会出现明显短板：

- Embedding 不可用（例如供应商欠费/鉴权失败）时，向量检索不可用或质量大幅下降
- 纯关键词问题（文件名、条款编号、业务术语）召回不稳定
- 大规模知识库场景下，向量检索可能存在“语义相近但不含关键字”的误召回，需要关键词检索补强

目标是在不牺牲现有向量能力的前提下，引入“生产可用、可运维、可扩展”的 BM25 关键词检索能力，并与现有上传/索引任务强绑定，避免数据漂移。

## 2. 目标

- 提供稳定的关键词检索（BM25）能力，支持 doc scope / global scope
- 与现有文档上传、增量索引、删除清理、全量重建流程一致
- 可观测、可回滚、可横向扩展
- 在 Embedding 失败时具备明确的降级路径（优先 BM25，再退到内容扫描）

## 3. 方案总览（分层与组件）

引入统一的“关键词检索服务层”与多后端实现：

- KeywordSearchService（统一接口）
  - upsert_doc_segments(doc_id, text, part_no, total_parts, title, updated_at)
  - delete_doc(doc_id)
  - search(query, doc_id=None, top_k=K, filters=...)
  - rebuild_all()
- Keyword Index Backend（可插拔）
  - Tier A（默认/轻量）：SQLite FTS5（内置 BM25）+ jieba 预分词
  - Tier B（生产/规模化）：Elasticsearch（默认 BM25）+ jieba 预分词（避免强依赖 IK 插件）

检索融合策略（Hybrid Retrieval）：

- 候选集 = VectorTopK ∪ BM25TopK ∪ GraphHints（可选）
- 归一化后加权融合：score = w_vec * vec + w_kw * kw + w_graph * graph
- Embedding 不可用或近期失败：跳过向量召回，直接走 BM25 + 图谱/内容扫描兜底

## 4. 数据建模（以“chunk”为索引粒度）

关键词检索不建议以“整篇文档”为粒度索引，原因：

- 对 LLM 上下文拼装不友好（需要再切分）
- 召回结果不可解释（用户希望看到命中文段）
- 评分容易被长文档稀释

建议统一以 chunk 为索引单元（400～800 字符，含 overlap）：

- chunk_id：全局唯一（doc_id + part_no + offset 或 hash）
- doc_id / title / filename：用于过滤与展示
- raw：原文片段（用于 sources 展示）
- tokens：预分词后的 token 串（用于 BM25）
- meta：页码/段号/时间戳/解析来源等

## 5. 索引构建与一致性（强绑定现有任务流）

### 5.1 绑定点位（推荐）

将 BM25 索引更新放在 KnowledgeDocument 的后台索引任务中（与向量索引同进度、同成功/失败语义）：

- 首段插入（快速可用）
  - 在首段 text 成功入库（向量/图谱）后，同步 upsert BM25（保证文档“刚上传就能搜”）
- 增量段插入（持续可用）
  - 每个 seg 写入向量后，upsert 对应 BM25 chunks
- 删除清理（避免脏数据）
  - 文档软删后，在实际清理任务完成时 delete BM25 doc chunks
- 全量重建（运维必备）
  - 在 vector rebuild 的运维入口旁，提供 keyword rebuild：对全部有效文档重新解析并重建关键词索引

### 5.2 幂等与去重

必须保证多次 upsert 不产生重复：

- chunk_id 作为唯一键
- upsert 使用“替换”语义（updated_at 变更触发重写）
- rebuild_all 先清空再重建（或按 doc_id 分批 replace）

## 6. SQLite FTS5 实现（Tier A：默认落地）

### 6.1 为什么作为默认

- 无需新基础设施，适合单机/小规模/边缘部署
- FTS5 内置 BM25 排序，性能与结果稳定
- 与当前默认 SQLite 环境兼容

### 6.2 中文分词策略

FTS5 默认 tokenizer 对中文不友好，采用“应用层预分词”：

- tokens = " ".join(jieba.lcut(raw))
- query_tokens = " ".join(jieba.lcut(query))
- FTS 查询使用 query_tokens

### 6.3 表结构建议

- kb_chunks：普通表（保存 raw、doc_id、chunk_id、title、meta、updated_at）
- kb_chunks_fts：FTS5 虚表（索引 tokens；raw/title/meta 设为 UNINDEXED）

一致性：

- upsert 时同时更新 kb_chunks 与 kb_chunks_fts
- delete_doc 时按 doc_id 删除两张表对应记录

### 6.4 适用边界

- 单机或小规模数据量（取决于文档总量与 chunk 数）
- 读写并发中等（FTS5 写入会有锁竞争，需要控制索引写入并发与批量提交）

## 7. Elasticsearch 实现（Tier B：生产级部署）

### 7.1 何时需要 ES

- 文档规模增长（chunk 数达到百万级以上）
- 多实例水平扩展（多后端 API 实例共享关键词索引）
- 需要更强的过滤、排序、聚合、同义词扩展与运营能力

### 7.2 索引设计建议

索引名：`kb_chunks_v1`

字段：

- chunk_id（keyword，主键）
- doc_id（integer）
- title/filename（keyword + text 可选）
- raw（text，store 用于展示）
- tokens（text，使用 whitespace analyzer）
- updated_at（date）
- meta（object）

分析器：

- tokens：使用 whitespace analyzer（因为 tokens 已是 jieba 分词后的空格串）

查询：

- match tokens（BM25 评分默认启用）
- doc scope 时加 filter：doc_id == X

### 7.3 写入策略

- 后台索引任务批量 upsert（bulk API）
- delete_doc 使用 delete-by-query（doc_id filter）或按 chunk_id 批量 delete
- rebuild_all 走离线批量导入，完成后索引别名切换（kb_chunks -> kb_chunks_v1_new），实现零停机切换

## 8. 检索融合（Hybrid）与降级策略

### 8.1 融合策略（推荐默认）

- VectorTopK：语义召回
- BM25TopK：关键词召回
- Merge 去重：按 chunk_id 或内容 hash
- 归一化：
  - vec_score 归一到 [0,1]
  - kw_score 归一到 [0,1]
- 融合打分：
  - score = 0.6 * vec + 0.4 * kw（默认，可配置）

### 8.2 Embedding 故障降级（生产策略）

- Embedding 最近失败（例如 5 分钟内）：
  - 跳过向量召回
  - 使用 BM25 +（可选）图谱/内容扫描兜底
- BM25 后端不可用：
  - doc scope 回退到内容扫描（substring + 覆盖度）
  - global scope 返回“关键词检索不可用”并提示用户缩小范围/指定文档

## 9. 生产级部署方案

本节给出两套可落地的生产部署档位，便于按规模与成本选择。

### 9.1 档位 A：单机/小规模（SQLite FTS5）

适用：

- 单机部署
- 知识库规模较小
- 不希望引入 ES

部署要点：

- 确认运行环境的 SQLite 编译包含 FTS5（启动自检：尝试创建 FTS5 虚表）
- 索引写入批量化，避免高频小事务（按 seg/批提交）
- 文件与 DB 放在持久化磁盘，避免容器重启丢失

监控要点：

- keyword_search_write_latency
- keyword_search_query_latency
- keyword_search_errors_total
- fts_db_size_bytes

### 9.2 档位 B：标准生产（Postgres + Elasticsearch）

适用：

- 多实例 API
- 数据规模中大型
- 需要 HA 与横向扩展

组件：

- Backend API（多副本）
- Postgres（主从或云托管）
- Elasticsearch（建议 3 master-eligible + data 节点起步，按容量扩展）

部署建议（Kubernetes 思路）：

- Backend：
  - Deployment 多副本
  - HPA 根据 CPU/延迟扩容
  - 通过环境变量配置 KEYWORD_BACKEND=elasticsearch
- Elasticsearch：
  - StatefulSet + PVC
  - 设置 resource requests/limits，避免 OOM
  - 开启 ILM 或定期清理旧索引（如采用版本化重建）

索引零停机重建（推荐）：

- 新建索引 kb_chunks_v1_2026xxxx
- bulk 导入完成后切 alias：kb_chunks -> kb_chunks_v1_2026xxxx
- 回滚：alias 切回旧索引

监控与告警：

- ES 集群健康（yellow/red）
- 查询 P95/P99 延迟
- bulk 写入失败率
- 索引大小增长与磁盘水位

安全：

- ES 与 API 之间走内网或 mTLS
- API 端对 query 进行长度与字符白名单限制，避免 query 造成资源消耗或注入风险
- 索引/日志中不记录用户敏感信息

## 10. 接口与前端集成建议

建议新增后端检索接口（仅示意）：

- GET /knowledge/search
  - params：q, scope(doc/global), doc_id?, top_k?, backend?(auto/vector/keyword/mix)
  - 返回：chunks（含 source=vector/keyword/scan），用于 UI 展示“命中来源”

前端建议：

- 在 sources 中增加展示标签：Vector / Keyword(BM25) / Scan
- 在 Embedding 故障期显示非阻塞提示：“语义检索不可用，已切换关键词检索”

## 11. 验收标准（生产可用）

- 功能：
  - doc scope：关键词命中可稳定召回对应 chunk
  - global scope：可跨文档召回，并能按 doc_id 过滤
- 一致性：
  - 文档上传完成后可检索
  - 文档删除清理后不可检索
  - rebuild 后结果与现有文档集一致
- 性能：
  - P95 延迟在可接受范围（按规模制定阈值）
  - 批量写入不拖垮 API（索引写入在后台任务，API 查询隔离）
- 运维：
  - 支持零停机重建（ES 档位）
  - 支持快速回滚（alias 切换）
  - 关键指标可观测，异常可告警

## 12. 继续优化方向（Roadmap）

- 引入“字段权重”：title/filename/正文不同权重
- 同义词与术语库：提升业务词召回（ES 同义词或应用层扩展）
- Query 改写：编号/缩写/拼音纠错与归一化
- Rerank：对融合候选做二次排序（可复用现有 RERANK 开关）
- 多租户与权限过滤：按用户/空间/标签过滤可见文档
