eah_agent的架构重构方案：内核逻辑与业务策略分离、领域模型中心化、基础设施插件化。
顶层架构重塑：四层模型
eah_agent/
├── domain/                # 【领域层】系统的灵魂，不依赖任何外部逻辑
│   ├── schemas/           # 全局 Pydantic 模型 (Intent, Plan, Task, State)
│   ├── interfaces/        # 协议定义 (BaseHandler, BaseProcessor, BaseTeam)
│   └── exceptions.py      # 领域特定异常
│
├── core/                  # 【内核引擎层】纯粹的管道编排，与具体业务无关
│   ├── orchestrator.py    # (原 control_plane) 异步并行调度引擎
│   ├── assembler.py       # (整合 builder/factory) 唯一负责生产 Agno.Agent 的流水线
│   ├── nlu.py             # 意图理解内核
│   └── stream_adapter.py  # 流式协议适配 (JSON/Markdown/Echarts)
│
├── handlers/              # 【应用策略层】根据意图分发的具体业务逻辑
│   ├── quick_handler.py
│   ├── plan_handler.py    # 内部调用 logic/planner.py
│   ├── flow_handler.py
│   └── data_handler.py
│
├── infrastructure/        # 【基础设施层】外部工具、存储、AI 供应
│   ├── mcp/               # MCP 协议实现
│   ├── persistence/       # (原 storage) 数据库与向量存储
│   ├── providers/         # LLM/Search 供应适配器
│   └── file_system/       # (原 file_orchestrator) 文件处理
│
├── logic/                 # 【专家逻辑层】复杂的算法或长流程
│   ├── planner/           # DAG 拆解与校验算法
│   ├── workflow/          # 状态机定义
│   └── team/              # 团队协作模式 (Research/Ops)
│
└── service.py             # 【API 入口】

2. 关键优化点：解决深度问题，重构后的结构是 “以领域契约为中心” 的：
A. 消除循环引用的“定海神针”：domain/ 层
现状： 你的 agent_planner 可能引用 agent_control_plane，而 control_plane 又要路由到 plan_handler。
方案： 所有的 数据契约（Pydantic 模型） 必须从 core 抽离，放入 domain/schemas/。
core 只负责按照 domain 的协议搬运数据。
这样，任何模块都可以引用 domain，但 domain 不引用任何人。这是解决 Python 复杂项目死锁的唯一标准解法。
B. 整合 builder 与 factory → Assembler（装配器模式）
现状： 你有 agent_builder.py 和 agent_factory.py。
方案： 采用 装配器（Assembler）模式。
建立一个 AgentAssembler 类，它是系统中唯一允许 import agno.agent 的地方。
它接收 AgentConfig（来自数据库），负责把 mcp、skills、llm、instructions 像装配零件一样组装成 AgnoAgent 实例。其他地方不直接创建 Agent。
C. control_plane 进化为 Orchestrator（编排器）
现状： control_plane 承载了太多业务判断。
方案： 将其改为纯粹的 并发调度器。
它应该利用 asyncio.gather 并发启动：NLU 分析、RAG 检索、用户权限检查。
它只负责维护请求的 状态机，具体的执行逻辑全部下沉到 handlers。
D. 插件化 infrastructure
现状： mcp 和 storage 散落在外。
方案： 将 mcp、e2b、file_processors 视为“插件”。
定义标准的 BaseToolkit 接口。
无论工具是来自本地 Python 函数还是远程 MCP Server，对于 core 引擎来说都是透明的。
3. 具体文件迁移建议
合并与清理 core：
删除 agent_service.py，逻辑移至顶层 service.py。
agent_title_generator.py 属于 logic 层，不属于内核。
agent_stream_normalizer.py 整合进 agent_stream_adapter.py，作为统一的流处理中枢。
细化 handlers：
把 file_orchestrator.py 和 file_processors.py 移入 infrastructure/file_system/。Handler 只应该负责调用，而不应该负责具体如何解析 PDF。
标准化 skills：
将 skills 目录重命名为 capabilities（能力层），它不仅包含本地函数，还包含对 mcp 的封装。
4. 工程“防腐”建议
配置版本化（Config Versioning）： 在 domain/config.py 中，确保 Agent 的配置（Prompt、Tools）支持版本号，方便线上进行 A/B Test。
全链路追踪（Observability）： 在 orchestrator 中内置 trace_id 的传递。Agent 的每一个子任务、每一次工具调用都必须带有该 ID，以便在 Grafana/LangSmith 中监控性能。
计算隔离： 对于 agent_executor，确保它调用的 sandbox（如 E2B 或 Docker）有严格的超时和资源限制。
